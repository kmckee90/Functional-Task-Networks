Use TRACE as a “scaled instantiation” experiment, not as a replacement for the current controlled results. The current paper’s claim is that support-conditioned mask selection gives both isolation and reusable computation: prior tasks can be protected while a new task gets lower pre-update head-start loss from recombining partially trained components. TRACE is useful because it already frames continual learning for aligned LLMs, uses eight sequential tasks across domain-specific, multilingual, code, and math/reasoning categories, and evaluates both task performance and degradation of general/instruction/safety abilities.

Implement the experiment with Qwen2.5-7B-Instruct as the primary model and Qwen2.5-14B-Instruct as a scale check only if compute permits. Do not use a base model for the main result, because TRACE is explicitly about aligned/instruction-following LLMs, and a base model adds prompt-format confounds. Qwen2.5 is a defensible choice because the released family includes instruction-tuned 7B and 14B models, among other sizes, and the technical report emphasizes improvements in instruction following, reasoning, coding, and broad knowledge. Use Qwen2.5-3B-Instruct only for debugging and hyperparameter sweeps; do not report it as the main evidence unless budget forces you to.

The task sequence should initially follow TRACE’s canonical order: C-STANCE, FOMC, MeetingBank, Py150, ScienceQA, NumGLUE-cm, NumGLUE-ds, 20Minuten. This order is visible in the TRACE detailed result tables and is the safest choice for comparability. Run one additional order as an order-sensitivity check, ideally the alternate order reported by TRACE: NumGLUE-cm, NumGLUE-ds, FOMC, 20Minuten, C-STANCE, Py150, MeetingBank, ScienceQA. If compute is tight, run the alternate order only for the main FTN-LoRA method and the strongest baseline, not for every ablation.

For each TRACE task, convert examples into the exact chat template used by Qwen2.5-Instruct. Train only on the supervised answer tokens, masking prompt tokens from the loss. Use the TRACE train/test splits and, if the full benchmark is too expensive, use the TRACE paper’s own reduced-data precedent: 500 or 1000 examples per task are explicitly reported in their data/epoch ablations. I would run 1000 train examples per task for the main 7B experiment, 500 for sweeps, and the full 5000 per task only if the method is stable and compute remains. TRACE states that it samples 5000 instances per task and balances classification tasks, so the full setting is reviewer-legible.

Define FTN-LoRA as follows. Freeze the Qwen backbone. Insert a bank of LoRA modules into attention q_proj, k_proj, v_proj, o_proj and MLP up_proj, gate_proj, down_proj. Use H LoRA atoms, each atom being a rank-r adapter contribution with its own A/B matrices. A mask selects k atoms per batch. The active adapter is the sum of selected atoms, scaled by alpha/k or alpha/r with the convention fixed across methods. Start with H=256 atoms, k=16 active atoms, rank r=4 per atom, LoRA alpha=16, dropout=0.05. If memory is high, reduce to H=128, k=8. If capacity is weak, use r=8 but keep H fixed. The key requirement is that all baselines see matched trainable LoRA parameter budget per active update, not necessarily matched total stored capacity.

Use support-conditioned mask selection exactly as the scaled analogue of the paper’s reconfig protocol: before each training update, sample a support minibatch from the current task, freeze LoRA and backbone weights, optimize only mask logits for S inner steps on support loss, project to hard top-k, then update only the selected LoRA atoms on a disjoint query minibatch. The current paper’s protocol fixes model weights during configuration, selects a binary top-k mask from a labeled support batch, and computes metrics on disjoint held-out data. Use S=10 for TRACE initially, not S=30; LLM inner loops are expensive. Run S=0 retrieval-only and S=5/10/20 on a 3B or 500-example sweep, then choose one value before the main run. Use AnnealSTE/top-k straight-through first, because the current draft found it best at small inner-loop budgets.

Use a small replay buffer, but keep it secondary. Store 100 examples per completed task, each with its selected mask. During training, draw one replay minibatch per current minibatch from stored examples whose mask overlap with the current mask lies in a middle band. Start with overlap fraction in (0.1, 0.7], because LLM LoRA masks may overlap more densely than the MLP setting. The paper’s current replay rule uses mask-overlap filtering to focus replay on interfering shared parameters, and the no-replay ablation shows replay carries a substantial share of retention. Report no-replay as an ablation, because otherwise reviewers may credit replay rather than support-conditioned reuse.

The central new metric is TRACE head-start. Before training task t, after completing tasks 1 through t−1, give the model a labeled support set from task t, select a LoRA mask or adapter according to the method, and evaluate on held-out task-t examples before any weight update. Report task-normalized accuracy/F1/exact-match where TRACE uses automatic metrics, and also report answer-token negative log likelihood to avoid generation-noise artifacts. This is the scaled version of the paper’s head-start loss, which is currently defined as support-conditioned mask selection on a new task followed by held-out loss before any new-task update. This metric is what turns TRACE from a forgetting benchmark into a test of both continual learning and knowledge transfer.

Report the standard continual-learning matrix R[i,j]: after training task i, evaluate tasks 1..i using each method’s no-task-identity inference rule. For FTN-LoRA, use support-conditioned mask selection at evaluation. For independent LoRA baselines, retrieve the stored adapter with lowest support loss. For sequential single-LoRA, there is no routing. Compute average final task score, average accuracy/performance over the lower triangle, forgetting, BWT, and forward/head-start transfer. Also run TRACE’s post-training general-ability, instruction-following, and safety evaluations if the harness is available; TRACE explicitly includes these deltas in addition to traditional CL metrics.

Baselines should be minimal but hard to dismiss. Run single sequential LoRA fine-tuning with the same active rank/parameter budget. Run sequential LoRA plus uniform replay with the same memory size as FTN-LoRA. Run independent per-task LoRA with oracle task identity; this is the upper bound for retention and the lower bound for transfer. Run independent per-task LoRA with support-set retrieval; this is the direct analogue of FixedMask+Router. Run a shared LoRA-bank with random fixed top-k masks per task plus retrieval, to test whether the bank alone is enough. Run FTN-LoRA without replay. Run FTN-LoRA with retrieval-only at evaluation, using stored training masks and no inner-loop test-time optimization; this is important because the current draft finds FTN+Router nearly matches FTN, implying training-time reconfiguration is the load-bearing ingredient.

Use one clean training budget across methods. For the 7B main experiment, use QLoRA or bf16 LoRA depending on hardware, sequence length 1024 or 2048, batch size via gradient accumulation to effective batch 64, learning rate 2e-4 for LoRA weights, cosine or constant schedule with 3 percent warmup, one epoch over each task in the 1000-example setting, max grad norm 1.0, AdamW with no weight decay on LoRA. Use greedy decoding for generative eval unless TRACE’s script prescribes otherwise. Fix three seeds for the main 7B canonical order if possible; if not, use two seeds plus the alternate order. For 14B, run one seed only as a scale sanity check comparing FTN-LoRA, sequential LoRA+replay, and independent LoRA+retrieval.

The exact claims to test should be pre-registered in the experiment README. FTN-LoRA is successful if it improves TRACE head-start over independent-LoRA retrieval and sequential LoRA+replay on at least six of eight tasks, while matching or improving average final retention relative to sequential LoRA and staying within a reasonable gap of oracle independent LoRA. The expected outcome is not that FTN-LoRA beats oracle isolation on final task accuracy; the paper already concedes that the method trades some retention ceiling for transfer. The strongest possible NeurIPS result is: oracle LoRA isolates but has weak head-start on new tasks; sequential LoRA adapts but forgets; replay helps retention but not transfer; FTN-LoRA gives lower pre-update loss/greater pre-update task score while retaining most prior-task performance.

The implementation deliverable should produce four artifacts: a JSONL log of every evaluation matrix entry with model, method, seed, order, train_task, eval_task, support_size, metric, and score; a head-start table by task and method; a final TRACE table with ACC/performance, forgetting, BWT, head-start, and general/instruction/safety deltas; and a mask-analysis table reporting mean overlap, overlap by task pair, and whether tasks from related categories share more LoRA atoms than unrelated categories. Do not overclaim category structure in TRACE unless the statistics support it. The safer mechanistic claim is that overlap predicts transfer: task pairs whose retrieved/optimized masks overlap more should show lower head-start loss or less adaptation loss.
